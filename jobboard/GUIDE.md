# Jobboard 잡 기록 가이드

잡보드에 잡을 기록하는 모든 이(사람, Claude 세션, 플랫폼 agent, dot)가 따르는 규칙이다.
agent는 포털 MCP의 `guide` 도구로 이 글을 읽는다. 규칙은 여기 한 곳에만 둔다.
스킬과 도구 설명은 이 글을 가리키기만 한다.

## 1. 잡의 칸

jobrun이 쓰는 칸(제목, 상태, 레시피, 서버, 출력 경로, 파라미터 값)은 고치지 않는다.
30초마다 jobrun 값으로 다시 써진다. 사람과 agent가 쓰는 칸은 아래와 같다.

| 칸 | 쓰는 것 | 언제 |
|---|---|---|
| `goal` | 무엇을 구하려는지, 한두 문장 | 제출(제안) 직후 |
| `why` | 왜 이 레시피·파라미터인지, 누구 요청인지 | 제출 직후 |
| `references` | 근거 자료: 문서, 앞선 잡(`::6hex`), 노트 | 있을 때 |
| `report` | 무엇이 나왔는지 (2절의 틀) | 잡이 끝난 뒤 |
| `files` | 출력 파일마다 한 줄 설명, 그림이면 해설 (3·4절) | 잡이 끝난 뒤, report와 함께 |
| `briefing` | 다음 단계 제안: 무엇을, 왜 | 결과를 보고 |
| `inputs` | 이 잡이 딛고 선 앞 잡들 (jobrun 파라미터로 정해지지 않은 경우만) | 흐름이 끊겨 보일 때 |

평가는 칸이 아니라 따로 쌓인다(`add_evaluation`). 5절을 본다.

## 2. report 틀

```
한 줄 결론 — 성공/실패와 핵심 숫자 하나 둘 (단위 포함)

수치 결과
- 측정량 = 값 ± 통계 오차 (단위), 몇 개로 구했는지
- …

그림
- 01_xxx.png 등 6장 — 해설은 각 그림 아래 (files 칸)

확인하지 못한 것
- 계통 오차, 빠진 run, 다음에 볼 것
```

- **그림 해설을 report에 쓰지 않는다.** 그림마다의 설명은 `files` 칸에 그 그림 이름으로 쓴다. 잡보드는 그것을 그 그림 바로 아래에 보여 준다. report의 "그림" 부분은 몇 장이 있는지와, 결론을 받치는 그림이 어느 것인지만 쓴다.
- 숫자에는 단위와 오차를 붙인다. 오차가 없으면 "오차 미산출"이라고 쓴다.
- 실패한 잡도 report를 쓴다. 로그에서 찾은 원인, 다시 할지 여부를 적는다.
- report는 화면에 쓴 그대로 보인다. 마크다운 표나 수식은 쓰지 않는다.

## 3. 그림 규칙

레시피가 그림을 그릴 때 지킨다. 지키지 못한 그림은 해설에 그 사실을 적는다.

1. **축 제목:** x축과 y축 제목을 반드시 쓴다. 변수 이름이 아니라 물리량 이름으로 쓴다.
2. **그림 제목에 cut:** 그림(캔버스) 제목에 그 그림을 만든 선택 조건(cut)을 쓴다. 예: `run 1240, NG HC >= 10, |z| < 50 mm, layer 91-111`. 조건이 길면 핵심만 제목에 쓰고 전부는 해설에 쓴다. 조건이 없으면 "no cut"이라고 쓴다.
3. **단위:** 축 제목에 단위를 붙인다. 예: `Drift velocity (cm/µs)`, `Counts / 2 mm`.
4. **통계 오차:** 통계 오차가 있는 양이면 오차 막대나 띠를 반드시 그린다.
5. **글자 크기:** 축 제목, 눈금, 범례는 보고서 본문 글자처럼 잘 보이게 키운다. 그림 높이의 4% 이상을 권하고, ROOT라면 `SetTitleSize`/`SetLabelSize` 0.045 이상이다.
6. **잘림 확인:** 축 제목, 눈금 숫자, 범례가 캔버스 밖으로 잘리지 않는지 저장한 파일을 열어 확인한다. 여백(ROOT `SetLeftMargin` 등)을 넉넉히 준다.
7. **한 그림 한 캔버스:** 비교가 목적인 것처럼 같은 파일에 여러 패널을 둘 이유가 없으면 그림마다 캔버스 하나로 따로 저장한다. 여러 패널로 묶었으면 해설에 그 이유를 쓴다.
8. **파일 이름:** 보여 줄 순서대로 `01_`, `02_`… 번호를 붙이고 내용이 드러나는 이름을 쓴다. 예: `01_drift_velocity_vs_E.png`.
9. **ROOT로 그린 그림:** 같은 이름의 `.root` 파일(캔버스나 히스토그램을 저장한 것)을 함께 출력 폴더에 남긴다. 예: `01_drift_velocity_vs_E.png`와 `01_drift_velocity_vs_E.root`. 잡보드 Results 탭에서 `.root`를 열어 확대하거나 값을 볼 수 있다.
10. **해설은 필수:** 그림마다 해설을 `files` 칸에 쓴다(4절). 해설 없는 그림은 끝난 잡으로 보지 않는다.

## 4. 그림 해설과 파일 설명 (`files` 칸)

출력 폴더의 **모든** 파일과 폴더마다 설명을 쓴다(`job.log` 빼고). `files`는 `{파일 이름: 설명}`이다. 잡보드는 그림이면 그림 아래에, 그 밖의 파일이면 파일 이름 아래 줄에 이 설명을 보여 준다. 설명이 없으면 그 자리에 경고가 뜬다.

예시(값은 자리표시):

```
update_job(id="<6hex>", files={
  "01_dedx_ratio_vs_layer.png": "layer별 low gain / high gain dE/dx 비 (트랙 평균, 오차는 평균의 표준오차). layer <a>–<b>에서 <값>±<오차>로 평탄하고, <c> 이후 오른다 → 이득 경계가 layer <c>.",
  "01_dedx_ratio_vs_layer.root": "01 그림의 TCanvas와 TGraphErrors(gRatio). ROOT로 보기에서 값 확인용.",
  "gain.txt": "layer별 이득 보정 계수 표: layer, gain, 오차; 112줄.",
  "log_scale_figures": "같은 그림들의 y축 로그 판(폴더). 꼬리를 볼 때만.",
  "redraw_linear.log": "그림을 선형 축으로 다시 그린 스크립트의 출력. 지워도 됨."
})
```

- **그림(png, svg, pdf…):**
  - 무엇을 그렸는지(축, 선택 조건, 데이터 범위)
  - 무엇이 보이는지(경향, 값, 이상한 점)
  - 여러 패널이면 그 이유
  - 그림 아래 캡션으로 보인다.
- **데이터(csv, root, txt…):** 열·객체가 무엇인지, 단위, 몇 개인지. 예: `scan.csv — 전압(V), E(V/cm), vz(cm/µs), dl·dt(√cm); 101줄`.
- **로그·중간 파일:** 무엇에 쓰는지 한 줄. 지워도 되는 것이면 그렇게 쓴다.
- **짝 파일:** `.root`처럼 그림의 짝인 파일도 따로 쓴다. 무엇이 들어 있는지(객체 이름과 종류)를 적는다.
- **폴더:** 무엇이 들어 있는지, 언제 보는지 쓴다.
- **해설 하나에 그림 하나:** 해설은 그 그림만 설명한다. 여러 그림을 함께 말해야 하면 report에 쓰고, 해설에서는 "report의 결론 2 참고"처럼 가리킨다.
- 이미 report에 그림 해설을 써 버렸으면 `files`로 옮기고 report에서는 줄인다.
- **`note`에도 쓰지 않는다.** 파일 설명은 `files`에만 쓴다. 도구 목록에 `files` 인자가 보이지 않는 세션(이 인자가 생기기 전에 시작한 세션)이라도 `update_job`에 `files`를 그대로 주면 서버가 받는다. 서버는 note에 파일 설명을 늘어놓으면 거절하고, 그림 해설이 빠진 채 report를 쓰면 빠진 그림 이름을 알려 준다.
- `job.log`는 설명하지 않아도 된다.

## 5. 평가와 커멘트

- **전체 평가:** "제안·평가" 탭에서 잡 하나에 대해 남긴다. 판정은 좋음 / 문제 / 보류 가운데 하나를 고르거나, 판정 없이 의견만 남긴다.
- **그림 커멘트:** Results 탭의 그림마다 남긴다. 축, 오차, 해석에 대한 피드백을 그 그림에 붙인다. agent는 `add_evaluation`에 `file`을 준다.
- **커멘트를 받은 agent:** 그림을 다시 그리거나 해설을 고친다. 고쳤으면 같은 그림에 "고침: 무엇을" 커멘트로 답한다.
- 평가와 커멘트는 지우지 않고 쌓인다.

## 6. 다음 단계 제안 (`briefing`)

- 다음에 할 잡을 레시피와 파라미터 수준으로 쓰고, 왜 그것이 필요한지 이 잡의 결과로 근거를 댄다.
- 여러 안이면 번호를 매기고 권하는 것을 먼저 쓴다.

## 7. 실행과 승인

- **잡 실행:** 실행은 언제나 사람이 받은편지함에서 승인한다. agent는 `submit_job`으로 후보만 남기고, `why`를 반드시 적는다.
- **결과 승인:** 결과 승인(`approve_job`)은 단계마다 정한 모드(사람만 / 규칙 자동 / agent 자동)를 서버가 판정한다. 거절되면 사람에게 승인을 요청한다.
- agent 승인은 사람이 확인하기 전에는 보고서 근거가 아니다.

## 8. 표기

- **잡:** 노트와 글에서는 잡을 `::6hex`(잡 id 끝 6자리)로 가리킨다. 잡의 태그는 `#job/6hex`다.
- **프로젝트:** 이름이나 하위 경로(`AToM-X/ihm`)로 쓴다.
